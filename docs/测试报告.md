## 一、被测对象与测试范围

系统对外共 4 个入口，本次测试全部覆盖：

| 编号 | 接口 | 方法 | 功能 | 是否本次重点 |
| --- | --- | --- | --- | --- |
| API-01 | `/` | GET | 首页导航 | 是 |
| API-02 | `/submit` | GET | 意见提交页（表单渲染） | 是 |
| API-03 | `/submit` | POST | 提交意见：落库 → 发 MQ 通知 → 清缓存 | **核心** |
| API-04 | `/list` | GET | 意见列表（Redis 缓存） | **核心** |

除页面功能外，还覆盖两条中间件链路：

- **读链路**：`/list` → `@Cacheable` 先查缓存，未命中回源 MySQL，写入 `feedbackList`（TTL 5 分钟）
- **写链路**：`/submit` → 落库 → 向 `feedback.exchange` 发 Fanout 通知 → `@CacheEvict` 清空列表缓存

**不纳入本次范围**：Redis / RabbitMQ 自身的高可用与集群、性能压测、安全渗透测试。

## 三、测试用例设计

### 3.1 使用的设计方法

| 方法 | 用于 |
| --- | --- |
| 等价类划分 | 用户名、意见内容的输入域划分 |
| 边界值分析 | 用户名字段 `varchar(50)` 的 0 / 1 / 50 / 51 / 300 字符 |
| 场景法 | 「提交后能否立刻在列表看到」等业务流程串联 |
| 错误推测 | 缺参数、纯空格、超长、重复提交等异常场景 |

### 3.2 等价类划分示例（username 字段，长度上限 50）

| 类别 | 划分 | 代表数据 | 预期 |
| --- | --- | --- | --- |
| 有效等价类 | 1–50 个非空白字符 | `张三`、50 个 `测` | 提交成功 |
| 无效等价类 E1 | 空字符串 | `` | 应拦截，提示必填 |
| 无效等价类 E2 | 全空格 | `   ` | 应拦截，视为空 |
| 无效等价类 E3 | 超过 50 字符 | 51 / 300 个字符 | 应拦截，提示长度超限 |
| 无效等价类 E4 | 参数缺失 | 不传 `username` | 应返回 400 并提示 |

每个无效等价类单独设计一条用例，这是用例设计的基本原则——一条用例只验证一件事，失败时才能定位到具体原因。

### 3.3 边界值取值

| 字段 | 字段类型 | 取下边界 | 取上边界 | 越上边界 |
| --- | --- | --- | --- | --- |
| `username` | `varchar(50)` | 0、1 字符 | **50 字符** | 51、300 字符 |
| `content` | `text`（上限 65535 字节） | 0、1 字符 | — | 5000 字符（仍可存） |

> 这里有一个容易踩的坑：`content` 是 `text` 类型，5000 字符根本不会触发任何错误。
> **写用例的预期结果之前必须先确认字段类型与长度上限**，否则会把「正常」误判成「缺陷」。

> **两条被撤销的误判，值得单独记下来**
>
> 1. **「内容未转义存在 XSS」——判断错了。** Thymeleaf 的 `th:text` 默认转义输出，
>    `<script>alert(1)</script>` 在页面上显示为文本而不是被执行。内容原样入库不是漏洞，
>    **输出时有没有转义才是关键**。用例 TC-013/014 最终判定为「通过」。
> 2. **「content 超长会返回 500」——判断错了。** 查表结构发现 `content` 是 `text`
>    （上限 65535 字节），5000 字符轻松存下；真正会因超长报 500 的是 `varchar(50)` 的 `username`。
>
> 这两条说明同一件事：**下结论之前先去验证事实**（看渲染结果、查表结构），
> 而不是按经验推断。判断缺陷归属的能力比执行用例本身更值钱。

## 五、缺陷清单

共发现 **4 处缺陷**，均为服务端缺失校验与异常处理所致。

### BUG-01　缺少必填校验，空值/全空格也能提交成功

| 项目 | 内容 |
| --- | --- |
| 严重程度 | 高 |
| 复现用例 | DEF-01（用户名为空）、DEF-02（用户名全空格）、DEF-03（内容为空） |
| 复现步骤 | `POST /submit`，`username` 传空字符串或全空格，`content` 传正常内容 |
| 期望结果 | 服务端拦截并提示「姓名不能为空」，不写入数据库 |
| 实际结果 | 返回 302 重定向到列表页，数据成功入库，列表页出现空提交人记录 |
| 根因分析 | `Feedback` 实体上没有任何校验注解，Controller 的 `@ModelAttribute` 参数也没有加 `@Valid`，因此参数校验这一环完全缺失。前端的 `required` 属性只挡浏览器，用 Postman 直接调接口即可绕过 |
| 修复建议 | 实体加 `@NotBlank(message = "姓名不能为空")`（`content` 同理），Controller 参数加 `@Valid`，配合 `BindingResult` 或全局异常处理返回友好提示 |

### BUG-02　用户名字段未做长度校验，超长直接返回 500

| 项目 | 内容 |
| --- | --- |
| 严重程度 | 高 |
| 复现用例 | DEF-04（username 传 300 字符） |
| 期望结果 | 提示「姓名最多 50 个字符」，返回 400 |
| 实际结果 | **HTTP 500**，页面暴露数据库异常信息 |
| 根因分析 | `username` 是 `varchar(50)`，超长时 MySQL 抛 `data too long for column`，异常无统一处理，直接冒泡到容器 |
| 修复建议 | 实体加 `@Size(max = 50, message = "姓名最多 50 个字符")` |

### BUG-03　缺少全局异常处理，参数缺失同样返回 500

| 项目 | 内容 |
| --- | --- |
| 严重程度 | 中 |
| 复现用例 | DEF-06（表单不传 `username`） |
| 期望结果 | 返回 400 并给出可读提示 |
| 实际结果 | **HTTP 500** |
| 根因分析 | `username` 为 `NOT NULL` 约束，MyBatis 抛出非空约束异常后无人处理 |
| 修复建议 | 增加 `@RestControllerAdvice` 全局异常处理器，把校验异常、数据完整性异常统一转换为 400 + 可读文案，不把堆栈暴露给前端 |

### BUG-04　列表页 `/list` 无访问控制，敏感内容全量公开

| 项目 | 内容 |
| --- | --- |
| 严重程度 | 高 |
| 复现用例 | DEF-07（未登录直接 GET `/list`） |
| 期望结果 | 未登录应跳转登录页或返回 401/403 |
| 实际结果 | HTTP 200，页面返回全部意见原文，包括提交人与完整内容 |
| 根因分析 | 系统未引入任何认证鉴权组件，`/list` 与其他接口一样对外完全开放 |
| 修复建议 | 引入 Spring Security 或轻量会话校验，`/list` 要求登录后访问；如面向全体员工公开，至少应做敏感词与匿名化处理 |

### 对照项（非缺陷）

DEF-05 验证 `content` 传 5000 字符可正常提交——因为 `content` 是 `text` 类型，
这是**符合预期的正常行为**，保留该用例是为了防止后续有人把字段类型改成 `varchar` 后无人察觉。

## 七、结论与改进建议

**结论**：系统主流程（提交 → 落库 → 通知 → 列表查询 → 缓存失效）功能正确，缓存与消息两条链路行为符合设计。
但在输入校验与访问控制上存在系统性缺失：**参数校验完全没有做**，任何绕过前端的人都能提交非法数据；
异常统一处理缺失，导致非法输入直接以 500 的形式暴露给使用者；列表页无鉴权，敏感内容全量公开。

**改进优先级**：

1. 加参数校验（`@Valid` + 校验注解），一次性解决 BUG-01 与 BUG-02
2. 加全局异常处理，解决 BUG-03 并统一错误响应格式
3. `/list` 加访问控制，解决 BUG-04
4. 缺陷修复后，把 `FeedbackDefectReproductionTest` 中的 7 条用例改写成「修复后的正确期望」，
   让它们从「证明缺陷存在」转为「防止缺陷回归」
